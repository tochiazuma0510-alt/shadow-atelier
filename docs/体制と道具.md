## Sol 運用 — 「数学は積極的に Sol」の制度設計(本 v2 の心臓)

ES7 の実戦が示した最大の教訓: **双方向の設計ループが最大の収穫源**(双方が相手の偽補題を検出・指示の外の自発提案が主要成果)。v1 はこれを「重要な岐路のみ」に絞っていた — **本案はこの絞りを撤回**し、ES7 原典の毎便双方向ループへ回帰・強化する。理由: 影工房では定義の正しさを機械(Lean/SAT)がまだ守っておらず、司令塔の数学が単独検証になる区間が長い。そこにこそ外部監査を常設すべき。

**便種 3 つ**:

1. **ゲート便(必須・スキップ不可)**
   - **定義ゲート**: Week 1 定義ノート確定前に Sol の敵対的レビュー。定義の取り違えは全下流を汚染する最悪バグ — ES7「反証前哨は証明予算投入前に必ず通す」の類推で「**実装予算投入前に定義監査を必ず通す**」。
   - **go/no-go 便**: Week 2 末の撤退条件判定(sprint 設計者としての Sol に現状を裁定させる)。
   - **定理候補便**: 「出たかもしれない」時の敵対的検証(ES7 どおり)。
2. **定例便(週次・Week 境界)**: その週の数学成果物(ノート・atlas 設計・証明スケッチ)一式を監査+次週設計の共同レビュー。
3. **随時便**: 数学的 stuck が 1 セッション続いたら召喚(技術的 stuck では呼ばない — ES7 規律 4 の区別を維持)。

**キックオフの型は ES7 を完全踏襲**: 冒頭 ■ 研究目的(不変の目的書への参照+今便の位置づけ 1 行)→ 分業宣言 → 数学と任務のみ・環境注意は書かない → **■ 司令塔の新候補開示**(毎便 1 件以上・価値見積もり+第一撃+撤退条件つき)→ Sol は報告書末尾に「考察と提案」(~30 行)→ **司令塔は次便冒頭で全提案に裁定**(採用/却下/保留+理由)。

**双方向裏取り(対等)**: Sol の主張は GAP+独立照合器で検算してから採用。こちらの設計・計算は Sol に反証させる。Sol の裁定も無謬扱いしない。

**研究者との分界(重要)**: Sol は**監査官であってユーザーの代理数学者ではない**。理解形成の主導はユーザー+コーチ枠。ただし Sol の反証・裁定文書はそのまま一級の教材として読書割当に載せる(ES7 の実戦記録が教材になったのと同型)。ユーザーは Sol への質問をキックオフに直接載せてよい(「■ 研究者からの質問」枠を常設)。

**コスト枠**: 定例便+ゲート便で週 2〜3 便を標準とし、この枠は本案の承認をもって**事前承認済み**とする(毎便の伺いはしない)。**2026-07-26 研究者明示: 週 2〜3 便は目安であり制約ではない — ペースは研究の必要と研究者の駆動で決まる**(超過の都度伺いは不要・停止ゲート 4 点は従来どおり)。

**ops と配達体制(2026-07-18 便 1 から自動化済み・ES7 §5 準拠)**: 郵便箱一式は `ops/` に移植済み(`ops/README.md` が正本)。要点:
- **配達はスクリプトが行う**(`ops/bin/launch_wake.ps1` — 司令塔の文章はファイル、 一行指示はポインタのみ)。Sol の返信はファイル到着を Monitor が自動検知(ユーザーの中継も done 通知も不要)。
- **セッションは Sol 便ごとに新規**(文脈はファイルで渡す)+便内フォローのみ pin resume。`--last` フォールバック廃止(多工房マシンでの誤 resume 防止)。
- **Sol は ops の便りを書かない**(数学成果物のみ)。運用連絡の定型はスクリプト、量が出たら ops 事務員(安価 subagent)を発足。Luna 発足時は**専用セッション+専用ピン**を新設し ops 便り担当は Luna(ES7 と同配置)。
- 既知の混線リスク: グローバル登録の es7ops MCP が影工房セッションにも露出(詳細と当面の運用は `ops/README.md`)。

## 文献ゲート(外部論文の解禁規約 — 2026-07-25 ユーザー裁定)

**原則**: 数学者二人(Opus・Sol)は**正典**(docs/week1-定義ノート.md+papers/ のコア論文)だけで独立に考えるのが既定。外部文献は**司令塔だけが読む関所**を通る。例外的解禁は 2 パターン:

- **① 要請駆動(遠征型)**: 数学者が具体的な技術的困難に当たり「解決できそうな文献はあるか」と問うたとき。**前提(2026-07-25 ユーザー明示): 技術的困難は関連分野では解決できない可能性が高い** — よって司令塔は関連分野に限らず**幅広い遠い分野**から機構を探し、工夫(翻訳)して要請に答える。近場を禁じるものではない — **見つかればどこでもよい**(同日ユーザー明示。遠征は期待値の置き方であって制限ではない)。「今の研究が進みそう」と判断した論文だけを降ろす。
- **② 司令塔発(常務型)**: **関連分野の文献は司令塔が能動的・継続的に読む**(発見待ちでなく常務)。使えそうなものは判断のうえ随時降ろす — 関連文献の主経路はこちら。
- **配達 SLA(2026-07-26 研究者確定)**: ①要請駆動は「**要請受領 → hunter 即出撃 → 探索完了 → 両数学者へ同時に渡す**」。探索完了が配達トリガーであり、便の境界・監査の儀式を待たない(速報 SendMessage/次接触の早い方で両者に同一の配達文書を届ける)。探索が長引く場合は中間報告を両者へ。
- **出口を止めるのは狭い場合だけ**: (a) **同一論点**のブラインド独立作業が相手側で進行中(答えの漏洩になる場合)、(b) 監査対象の主張**そのもの**の成否を文献が直接与えてしまう場合(アンカリング)。この 2 条件に当たらない配達を止めない。正否に関わる発見(反例・既証明)は従来どおり局面を問わず即時開示。

**運用**:
- 候補検索は**二部隊制**(2026-07-25 ユーザー指示で分離): **① 遠征検索 = paper-hunter(opus/medium・常設)** — 技術的困難は単純検索では見つからないため、困難を機構の言葉に抽象化し「どの遠い分野に解の形がありそうか」の**当たり付け判断**込みで探す。**② 関連分野検索 = paper-scout(sonnet/medium・常設・据え置き)** — 関連分野の定例スイープ・目録更新。いずれも検索方式は司令塔がスペックで指定し、採否は判断しない — 実在確認済み候補リスト+照合観点まで(報告書: docs/scout/)。
- 読解は司令塔(数式の精密抽出が要るときは reader 併用)。
- **配達の形(2026-07-26 ユーザー確認・同日強化)**: 降ろすときは**論文そのもの**(PDF を papers/delivered/ に配置・ハッシュを LEDGER)+**司令塔の翻訳覚書**のセットが既定。覚書だけで済ませない。**配達文書で引用した論文は配達時に一括取得して置く**(arXiv 等の合法入手可能分。誌面のみで入手不能なものだけ書誌+入手経路の注記で渡す)。**原著は資料庫であり全読の義務はない**(2026-07-26 研究者明示)— 覚書で足りるなら読まなくてよく、精読の範囲は数学者の裁量。読んだ範囲は従来どおり申告(出所規律)。
- **降ろすときは司令塔の「一工夫」を義務とする**(ユーザー明示「既存と全く同じことをしてもそれは解決にならない可能性が高い」): 論文をそのまま渡さず、機構を抽出し、B₃-gentle 設定(hexagon のみ・pentagon なし・c 中心・NFI_PB₃(B₃)・有限商)への翻訳・仮定の照合・適用の形を添えて渡す。
- 数学者側の作法: 文献が要ると思ったら成果物に**【文献要請】**(困難の記述+欲しい結果の型)を書く(mathematician は成果物内・Sol は返信の P# で)。自分で外部文献を漁らない。
- 降ろした論文・一工夫の内容・きっかけ(①/②)は LEDGER に記録(出所管理)。
- **検疫圏**: docs/scout/(scout 報告書+司令塔の文献ノート)は**数学者(mathematician・Sol)の読み取り禁止圏**。司令塔の予習はここに蓄積し、ゲートを通るときだけ翻訳を添えて渡す(予習の漏出はゲートの実質破りになるため)。**→ 2026-07-25 改訂: 下の配置図が本則(docs/scout/ は開示済みアーカイブへ・未開示は金庫へ)。**

## 基盤の差分

- **git 化(即時提案)**: 影工房はまだ git repo でない。SHA 束縛・`git ls-files` 検証・Sol 便の `git status` 監査・将来の Actions 工場はすべて git 前提 — **`git init` を本案承認と同時に実施**(public 化は別途停止ゲート)。
- **ブラインド・ファーストの適応**: Week 1-2 は文献**再現**が任務なのでブラインド不適用。Week 3-6 の atlas(新規対象)では「列挙は事前登録した仕様から・genuine 判定は証拠から・文献の予想値に答えを錨づけしない」形で精神を継承。**追記(2026-07-25・事故から)**: ブラインド工程(独立起草・封印予測)の進行中は、**片側の成果物を共有ツリー(docs/ 等)にコミットしない** — 相手エージェントが読める場所に置いた時点でブラインドは破れる(便 05 (e) で実発生・LEDGER 続報 3)。突合完了まで scratchpad か検疫圏で保持する。
- **統計**: campaign_stats.mjs は Lean セッション前提のためそのまま使わない。週次で軽量手動集計(Sol 便数・提案採用率・較正ゲート通過率・UNKNOWN 件数)から始め、道具化は必要が生じてから。
- **ハードウェア(2026-07-18 ユーザー明示: この PC は RAM 8GB)**: ES7 のハイブリッド原則そのまま(ローカル対話+クラウド工場)。運用規則: ①GAP は `gap.ps1` のヒープ上限 -o 2g つき(暴走で PC を巻き込まない)②作業指示書に容量見積もりと cap を必記 ③Lean 常駐サーバ(2.5–3GB)は使用時だけ起動・大規模 GAP と同時に走らせない(排他運用)④大規模列挙・一括 Lean 検証はローカル禁止 — GitHub Actions(public 化・停止ゲート経由)か Codespaces(~$1・ES7 実証)へ ⑤新種の計算は小さく撃って実測 RAM を LEDGER に記録してから拡大。
