## Sol 運用 — 「数学は積極的に Sol」の制度設計(本 v2 の心臓)

ES7 の実戦が示した最大の教訓: **双方向の設計ループが最大の収穫源**(双方が相手の偽補題を検出・指示の外の自発提案が主要成果)。v1 はこれを「重要な岐路のみ」に絞っていた — **本案はこの絞りを撤回**し、ES7 原典の毎便双方向ループへ回帰・強化する。理由: 影工房では定義の正しさを機械(Lean/SAT)がまだ守っておらず、司令塔の数学が単独検証になる区間が長い。そこにこそ外部監査を常設すべき。

**便種 3 つ**:

1. **ゲート便(必須・スキップ不可)**
   - **定義ゲート**: Week 1 定義ノート確定前に Sol の敵対的レビュー。定義の取り違えは全下流を汚染する最悪バグ — ES7「反証前哨は証明予算投入前に必ず通す」の類推で「**実装予算投入前に定義監査を必ず通す**」。
   - **go/no-go 便**: Week 2 末の撤退条件判定(sprint 設計者としての Sol に現状を裁定させる)。
   - **定理候補便**: 「出たかもしれない」時の敵対的検証(ES7 どおり)。
2. **定例便(週次・Week 境界)**: その週の数学成果物(ノート・atlas 設計・証明スケッチ)一式を監査+次週設計の共同レビュー。
3. **随時便**: 数学的 stuck が 1 セッション続いたら召喚(技術的 stuck では呼ばない — ES7 規律 4 の区別を維持)。

**キックオフの型は ES7 を完全踏襲**: 冒頭 ■ 研究目的(不変の目的書への参照+今便の位置づけ 1 行)→ 分業宣言 → 数学と任務のみ・環境注意は書かない → **■ 司令塔の新候補開示**(毎便 1 件以上・価値見積もり+第一撃+撤退条件つき)→ Sol は報告書末尾に「考察と提案」(~30 行)→ **司令塔は次便冒頭で全提案に裁定**(採用/却下/保留+理由)。

**双方向裏取り(対等)**: Sol の主張は GAP+独立照合器で検算してから採用。こちらの設計・計算は Sol に反証させる。Sol の裁定も無謬扱いしない。

**研究者との分界(重要)**: Sol は**監査官であってユーザーの代理数学者ではない**。理解形成の主導はユーザー+コーチ枠。ただし Sol の反証・裁定文書はそのまま一級の教材として読書割当に載せる(ES7 の実戦記録が教材になったのと同型)。ユーザーは Sol への質問をキックオフに直接載せてよい(「■ 研究者からの質問」枠を常設)。

**コスト枠**: 定例便+ゲート便で週 2〜3 便を標準とし、この枠は本案の承認をもって**事前承認済み**とする(毎便の伺いはしない)。随時便・枠超過は都度ユーザーに見積もり提示(改装係数つき — ES7 コスト規律)。

**ops と配達体制(2026-07-18 便 1 から自動化済み・ES7 §5 準拠)**: 郵便箱一式は `ops/` に移植済み(`ops/README.md` が正本)。要点:
- **配達はスクリプトが行う**(`ops/bin/launch_wake.ps1` — 司令塔の文章はファイル、 一行指示はポインタのみ)。Sol の返信はファイル到着を Monitor が自動検知(ユーザーの中継も done 通知も不要)。
- **セッションは Sol 便ごとに新規**(文脈はファイルで渡す)+便内フォローのみ pin resume。`--last` フォールバック廃止(多工房マシンでの誤 resume 防止)。
- **Sol は ops の便りを書かない**(数学成果物のみ)。運用連絡の定型はスクリプト、量が出たら ops 事務員(安価 subagent)を発足。Luna 発足時は**専用セッション+専用ピン**を新設し ops 便り担当は Luna(ES7 と同配置)。
- 既知の混線リスク: グローバル登録の es7ops MCP が影工房セッションにも露出(詳細と当面の運用は `ops/README.md`)。

## 検証の網の適応

- ES7: kissat ↔ drat-trim。影工房: **GAP(探索)↔ node 照合器(独立再計算・cross-check)↔ Lean decide(検証・常駐サーバ既設)**。**用語規約(2026-07-18 ユーザー指示): 「検証(verified)」は Lean に予約** — 二系統一致は「照合済み(cross-checked)」。三層目の Lean 化は証明書形式が固まってから(Week 2 で形式を設計)。
- **Lean 基盤の使用権(2026-07-18)**: 証明工房(ES7)はプロジェクトとして畳む方針とユーザー決定 — 常駐 Lean サーバと atelier_lean はインフラとして影工房が常用してよい(資源競合なし)。**接続の分業**: 司令塔が証明書形式(JSON)を設計 → **Luna が checker/decide 証明を実装(xhigh・ES7 formalizer 配置の継承)** → Sol が数学的正しさを監査 → 司令塔が独立検証と統合。司令塔・Sol は Lean 実装をしない。使い方の正本: `docs/道具と検証の序列.md` §C。
- **較正ゲート**(n17 ゲートの移植): 答えを知っている問題 = 2405.11725 Thm 4.3 の GT(K(n)) 明示記述と 2 冪の既知結果。**これが通るまで新規対象(奇数/混合位数)には撃たない**。
- 宇宙の事前登録・UNKNOWN 一級・主張の台帳(verified/candidate/UNKNOWN/refuted)・既知例三分・versioned 規律: v1 のまま(変更なし)。

## 基盤の差分

- **git 化(即時提案)**: 影工房はまだ git repo でない。SHA 束縛・`git ls-files` 検証・Sol 便の `git status` 監査・将来の Actions 工場はすべて git 前提 — **`git init` を本案承認と同時に実施**(public 化は別途停止ゲート)。
- **ブラインド・ファーストの適応**: Week 1-2 は文献**再現**が任務なのでブラインド不適用。Week 3-6 の atlas(新規対象)では「列挙は事前登録した仕様から・genuine 判定は証拠から・文献の予想値に答えを錨づけしない」形で精神を継承。
- **統計**: campaign_stats.mjs は Lean セッション前提のためそのまま使わない。週次で軽量手動集計(Sol 便数・提案採用率・較正ゲート通過率・UNKNOWN 件数)から始め、道具化は必要が生じてから。
- **ハードウェア**: ES7 のハイブリッド原則そのまま(ローカル対話+クラウド工場)。GAP の atlas 列挙が 8GB を超えたら Actions 工場(ES7 教訓集は v1 から継承済み)。
