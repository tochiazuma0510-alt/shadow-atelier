## 1. 三レーンの定義

### Lane S(探索・Search)

- **入力**: 窓定義 NW(7)(`docs/notes/hs_prop7_translation_v1.md` §8.7.3 定義 NW(p) を p=7 で固定)。exact pc presentation of P = F₂/(γ₅(F₂)F₂⁷)(発火条件2 の stage1 相当を独自実装で再構築 — 継承しない、§3 参照)。
- **やること**: 簡約 hexagon **(3.10)(3.11)** だけを使って、P 内の charming candidate `(m, f̄)`(m ∈ 𝒳_N, f̄ ∈ [P,P])を**悉皆列挙**する。これは P100-1.2 条件 3 の「hexagon 判定」を担う。
- **出力**: GT-shadow 候補集合 `{(m, f̄)}` の cert(件数・列挙全リストまたはハッシュ・使用した簡約 hexagon の式の逐語)。
- **やらないこと**: full B₃/N 上の (3.3)(3.4) は評価しない。K(0,5)/W にも触れない。

### Lane V(検証・Verify)

- **入力**: 窓定義 NW(7)(Lane S と同じ紙の定義から独自に再構築 — NW-1a/NW-1b の証明を辿って B₃/N を**自前で**組む。Lane S の出力にある P の GAP オブジェクトそのものを import しない)。Lane S の出力候補リスト(**値だけ**を受け取る — `(m, f̄)` の組の集合、GAP オブジェクトや中間表現は受け取らない)。
- **やること**: **full B₃/N** 上で **(3.3)(3.4)** を評価し、Lane S の各候補が真に GT(N) の元であることを独立に再判定する。これが「探索と検証の helper 非共有」(定義ゲート項目 2)の検証半分。
- **出力**: 各候補について PASS/FAIL の再判定結果。Lane S との**不一致件数**(0 が期待値 — 不一致は品質問題であり S-9 停止の対象、§5)。
- **やらないこと**: K(0,5)/W には触れない。Lane S の中間コード(hexagon 判定関数の実装そのもの)を読まない。

### Lane P(pentagon・PENT)

- **入力**: 窓定義 NW(7)。Lane S(または Lane V — どちらの通過集合を使うかは司令塔が cert 突合時に指定。**両方に対して独立に走らせるのが望ましい**、§4)の候補**値**リストのみ。
- **やること**: K(0,5)/W(W = γ₅(K(0,5))K(0,5)⁷)上で `PENT_W([m, f̄]) ⟺ ρ⁴(f̄)ρ³(f̄)ρ²(f̄)ρ(f̄)f̄ = 1` を判定する。K(0,5) の構成(B₄ Artin 表示 → PB₄ の RS → Δ₄² での商 → sphere row-product 辞書 → ρ)は**発火条件 2 で既に構築・fail-closed アンカー全 PASS 済みの資産**(`search/probe/hsp7_gap_v1/stage1_pb4.g`, `stage2_k05.g`)であり、**Lane P だけがこれを継承してよい**(§3)。
- **出力**: 各候補の PENT PASS/FAIL、NW-P6(h₄ᵗ family の t=0..6 個別判定)・NW-P7(p=5 control)・NW-P8(N vs N₀ の c 依存性)は**すべてこのレーンの担当**(§5)。
- **やらないこと**: hexagon 判定はしない(受け取った候補集合を前提として扱う)。B₃/N 側の (3.3)(3.4) を再評価しない。

### interface 図(データフローのみ・実装は含まない)

```
        NW(7) の紙の定義(§8.7)
           |         |         |
      (各レーンが独自に P/B3N/K05W を実装)
           |         |         |
       [Lane S]  [Lane V]  [Lane P]
           |         |         |
      candidates  --(値のみ)-->  Lane V
           |                     |
      candidates  --(値のみ)----------------> Lane P
                                               |
                                        PENT 判定 + NW-P6/7/8
                                               |
                                     司令塔突合(3 cert を並べて手で比較)
```

Lane 間を流れるのは**候補の値(m の整数値・f̄ を語または正規形で表した文字列)のみ**。GAP オブジェクト・中間関数・helper モジュールは一切流れない。

## 3. 既存 stage1-4 資産の継承先 — 提案: **Lane P に限定継承**

### 提案

`search/probe/hsp7_gap_v1/stage1_pb4.g`(B₄/PB₄ 構築)・`stage2_k05.g`(K(0,5) 構築・辞書・fail-closed アンカー)・`stage3_gen_setup.g`(バッチ setup 生成手順)は **Lane P にのみ継承させる**。Lane S・Lane V はこれらを import せず、それぞれ独立に(Lane S は P だけを、Lane V は B₃/N を)ゼロから構築する。

### 理由

1. **K(0,5) の構築は Lane P 固有の対象**である。Lane S(P のみが要る)・Lane V(B₃/N のみが要る)はそもそも K(0,5) 側のコードを必要としない — 継承の候補にすらならない。
2. **P 自体の構築(stage1 の一部・F₂ の p-quotient)は Lane P も Lane S も必要とするが、これは「helper」ではなく「対象そのものの定義」**である。定義ゲート項目 2 が禁じているのは「探索で使った**判定ロジック**(hexagon 評価関数)を検証レーンが検算なしに信用して使う」ことであり、「P という群を GAP でどう構築するか」という**共通の土台**まで別々に発明し直すことまでは要求していない、というのが自然な読みである。ただし本稱の原則(冒頭)により Lane S は「P の構築」は自前で行い、stage1/2/3/4 のいずれも import しない(P の構築自体は軽量で、独自実装の負担は小さい)。
3. **CV-9 の観点**では、Lane P が発火条件2の資産をそのまま使うことは「同一著者・同一 helper」の連続性を持つが、これは Lane P **単体の内部**の話であり、Lane S/V との**独立性**を損なわない(Lane P と Lane S/V が独立であることが helper 非共有の目的であって、Lane P 自身が発火条件2との連続性を持つこと自体は問題ではない — cert の著者表(§7)にその連続性を明記すればよい)。
4. 発火条件2で fail-closed アンカー(K(0,5)^ab=Z⁵・ρ well-defined・ρ⁵=id・ρ≠id)を全 PASS しているため、**Lane P が K(0,5) をゼロから作り直すコストは検証価値に対して割に合わない**(むしろ作り直すと「同じ辞書を独立に導出できるか」という**別の実験**になり、それは条件4の範囲外 — 辞書の精読照合は Sol ゲート案件、§0 の状態表参照)。

### 継承しないもの(Lane P 内でも新規に書くべきもの)

- h₄ の評価・N_ρ の評価そのもの(発火条件2の stage4 は「m=0, t=1 の 1 点」しか見ていない。Lane P は NW-P6 に従い t=0..6 の 7 点全てを評価する新規コードが要る)。
- Lane S/V から受け取った候補集合全体に対する PENT_W の一般判定ループ(発火条件2は決め打ちの h₄ᵗ family のみ)。

## 5. 各レーンの cert 様式と司令塔突合の手順

### 5.1 cert 様式(共通骨格・レーンごとに固有欄を追加)

各レーンの cert は独立ファイルとする(1 レーン = 1 cert、または 1 レーン内で複数の走に分けても構わないが、レーンをまたいで 1 ファイルに混在させない)。命名案:

- `search/certs/hsp7_cond4_laneS_p7_YYYYMMDD.json`
- `search/certs/hsp7_cond4_laneV_p7_YYYYMMDD.json`
- `search/certs/hsp7_cond4_laneP_p7_YYYYMMDD.json`

共通骨格(`hsp7_cond2_p7_20260804.json` の schema を土台に拡張):

```
{
  "schema": "hsp7-cond4-lane{S|V|P}/v1",
  "DRIVER_DONE": true,               <- 軽微指摘(裁定435)への対応: 完走マーカーをトップレベルに明示
  "lane": "S" | "V" | "P",
  "generated_by": [...driver scripts, このレーン専用...],
  "imports_declared": [...このレーンが読んだファイルの網羅リスト。§2の禁止表と突合可能な形で...],
  "imports_forbidden_check": {"other_lane_scripts_referenced": false, "other_lane_gap_objects_referenced": false},
  "universe": {...NW(7)固定、p, class_bound, exponent...},
  "candidates_in": [...他レーンから受け取った値のみのリスト。cert内で完結し、他certへの参照はハッシュのみ...],
  "candidates_in_source_cert_sha256": "...",
  "lane_specific_results": {...レーン固有(§1参照)...},
  "stop_rules": {"S6":..., "S7prime":..., "S8":...},
  "cross_checked_status": {"status": "n/a", "reason": "single lane; 3レーン揃ってCV-9判読後に格上げ"},
  "provenance": {...}
}
```

### 5.2 司令塔突合の手順

1. 3 レーンの cert が揃った時点で、司令塔(または委嘱された係)が**3 ファイルを並べて**候補ごとに (Lane S の判定, Lane V の判定, Lane P の判定) の 3 つ組を作る。**この突合作業自体もレーンの外(第四の主体)が行う** — いずれかのレーンの driver に突合ロジックを埋め込まない。
2. Lane S と Lane V が全候補で一致することを確認(不一致は S-9 で停止・保留)。
3. 一致した候補集合に対して Lane P の PENT 判定を読み、NW-P6 の「ちょうど 1 個 PASS」を確認。
4. NW-P2 型の全予言(NW-P6/P7/P8)との突合表を 3 cert から機械的に合成し、`search/certs/hsp7_cond4_summary_YYYYMMDD.json` のような**四つ目の集約 cert**(これは判定を行わない、3 cert の値を転記・突合するだけの文書)を作る。
5. CV-9(falsifier による規約同一性判読)へ 3 cert + 集約 cert を提出。ここで初めて「cross-checked」を名乗れる(それまでは各レーン単体は single-lane candidate のまま)。

## 6. CV-9 判読に耐える独立性 — 著者・helper・規約の分離表
