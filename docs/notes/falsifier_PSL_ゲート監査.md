## 1. 漏れ狩りの詳細(最重要項目)

### 1a. 機械確認(grep)— リテラルな封印値は spec に**存在しない**

- `42`・`54`・`110`・`32`・`40`・`48` の数字列(sealed の total/gt_count 相当)・`PS-F14`・`PS-F12b` の文字列は `search/manifest_spec_v2_psl.md` に **一件も出ない**(正本にはある `## 2.4 期待値(sealed)` の節ごと・PU-F12 の相方説明ブロック・PU-F14 の (b) 裁定の理由ブロックが spec では丸ごと欠落しており、正しく削除されている)。
- `n_m` という**フィールド名**はスキーマ内(証明書の出力欄名として)残っているが、これは正本の disclosure 表(§0)でも「渡す」対象(スキーマの欄名そのものは spec)であり、値ではない。ここは正しい。

### 1b. 【要修正】残存する間接的漏れ — PU-F14 と §2.0 の $e$ 列

正本 §3 の PU-F14 直後の説明ブロック(spec では削除済み)に、司令塔自身の言葉で次が明記されている:

> 「司令塔裁定(2026-07-26): (b) 採用 — 期待値列(**7・8・7・9・11・10・12**)は PS-F14 として sealed」

この期待値列 **7,8,7,9,11,10,12** は、§2.0 宇宙表の **$e$ 列**(S1..S7: 7,8,7,9,11,10,12)と**完全に一致**する。つまり $\lvert C_{\mathrm{Aut}(\hat G)}(w)\rvert = \mathrm{ord}(w) = e$ が全 7 窓で成り立つという事実そのものが、この裁定文の中で暗黙に確認されている。

- $e$ は PU-F2 の期待値として **spec に残さざるを得ない**(正本もこれを「漏れの増分は『$\lvert C\rvert=e$ という一行』である」と自認している)。
- したがって **spec だけを読んだ実装担当は、$e$ 列を見た時点で PU-F14 の答え($\lvert C_{\mathrm{Aut}(\hat G)}(w)\rvert$)を機械的に予測できる**。これは「一切残っていない」という監査目標には**厳密には反する**(司令塔が意識的に許容した残り漏れであり、隠れた新規の穴ではない)。
- **より重い懸念(空虚性・checklist 項目 1)**: PU-F14 の目的は「`AutomorphismGroup` に頼らず明示的な共役元/Frobenius で $\mathrm{Aut}(\hat G)$ を構成する」機構を較正することである(§1.1 末尾)。もし実装担当が($e$ との一致に気づいて、あるいは気づかずに)$\lvert C_{\mathrm{Aut}(\hat G)}(w)\rvert$ を明示構成せずに $e$ をコピーして出力しても、この漏れのため**数値としては「通ってしまう」**。つまり PU-F14 は「答えを知っている問題が機構を実際に通るか」を保証できておらず、**機構をバイパスしても検出されない較正ゲート**になっている可能性がある。
- **提言**: PU-F14 の証明書要件に「明示 conjugator/Frobenius 生成元による構成過程(中間 witness)を残す」ことを追記し、単なる整数出力だけでは fixture PASS にしない設計に強化するべき。これを行わない場合、この一致は「較正の空虚化」の実例として `docs/notes/` に恒久記録するのが筋。

## 総括

新規の致命的な穴(封印値のリテラルな漏出・宇宙表の矛盾・fixture 構成の破綻)は見つからなかった。唯一の実質的な指摘は、**PU-F14 の期待値が $e$ 列から機械的に予測可能である**という、司令塔自身が既に自認・裁定済みのトレードオフについて、**その較正ゲートとしての空虚化リスク(機構バイパスの検出不能性)**が manifest 側で未対処である点。これは WO4 を止める理由にはならないが、証明書スキーマへの中間 witness 追記を伴う軽微な修正を推奨する。
