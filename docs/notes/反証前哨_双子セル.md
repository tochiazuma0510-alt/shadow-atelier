## 1. 較正①「二構成全単射一致」— marked factor map 経由か

## 4. staged counts の排他性・hexagon 語規約(A5-CONV)

- `search/week3-battery-common.g` L315-372 `EnumerateReducedHexagon`(GAP 側の正本、twincell
  はこれを import して使い回している、L32/130 で確認)は各 `(f, m)` の組み合わせを

  if-continue 制御フロー**で分類しており、コード構造上、同一候補が複数カテゴリに二重計上され
  ることはあり得ない(L343-366、各 `continue` が次のカテゴリ判定に進むのを阻止)。
  `crosscheck/check-twincell.mjs` L172-190 の独立実装も同型の if-continue 構造。
  両者は「shadow_sum_identity」(candidate_total - h10 - h11 - genFail = shadow_total)を
  それぞれ独立に検算しており(GAP側 L135-137、node側 L247-248)、5証明書全てで
  `shadow_sum_identity:true` を確認した(本監査でも `node crosscheck/check-twincell.mjs` 実行
  で再確認、全 PASS)。
- L315-372 のコメント(week3-battery-common.g L722-728、本監査で確認)によれば
  `EnumerateReducedHexagon` は「quotient shortcut」(`GroupHomomorphismByImages` で実際の
  θ/τ 準同型を群要素に対して直接評価する方式)を使っており、そもそも語規約(prepend/natural)の
  区別が発生しない設計。一方 `check-twincell.mjs` の独立再実装(L133-161)は**語レベル**
  (BFS+prepend 規約)で θ/τ を再現しており、GAP 側とは異なる評価方式でありながら5証明書全てで
  数値が一致した。これは「A5-CONV」規約(`docs/週次定義ノート §1.5.4` 系)がこの独立系でも
  正しく再現されていることの傍証にはなるが、**この監査では A5-CONV 適合テスト
  (`ev(yx^-1) = (1 2 4)`)そのものを twincell 系列(行列 mod L 構成)に対して直接実行した
  形跡は見当たらなかった**(A5-CONV は既存の PSL 系列 `search/manifest_spec_v2_psl.md`
  `PU-F11` で別途通されているものであり、twincell の行列 mod L 構成に対する専用の
  適合テストではない)。
  → **【軽微】**: 数値一致(5/5 全証明書 PASS)は強い状況証拠だが、A5-CONV 適合テストを
  twincell 固有の構成(行列 mod L)に対して明示的に走らせた記録がない。既存 PSL 系列で
  通っている規約を「そのまま使い回して問題ない」という前提は、今回初めて a-系統(行列)の
  θ/τ 評価が絡む場面なので、発射前に一度 A5-CONV 相当の最小テストを twincell 側でも
  明示的に走らせておくとより安全(必須ではないが安価)。

## 5. 負例 fixture・BONUS 観測の扱い

### 5a. 負例 fixture(WRONG_LEVEL6)は実際にバグ検出力を持つか — 実測で確認 PASS(この観点では穴を見つけられなかった)

- 本監査で `node crosscheck/check-twincell.mjs` を実際に実行(改変なし)。結果:
  ```
  window C8_matrix_WRONG_LEVEL6_fixture: PASS
  ...
  [PASS] NEGATIVE FIXTURE (wrong level L=6) correctly rejected: bijection_ok=false, shadow_total=6
  ```
  「window ...: PASS」は**証明書の自己無矛盾性**(claim=recompute)の意味であり、これは
  正しく振る舞う(fixture は正直に作られているので自己矛盾はない)。実際の負例判定は別の行
  `NEGATIVE FIXTURE ... correctly_rejected` であり、`calibBad.ok=false`(bijection 不成立)
  かつ `shadow_total=6≠4` の**両方**が検出されている(L370-373)。総合判定 `all_ok`
  (L383)にも `negFixtureOk` が組み込まれており、これが false になれば `all_pass` は
  出ない設計になっている(fail-closed)。
  → **【軽微】表記上の紛らわしさ**: `window C8_matrix_WRONG_LEVEL6_fixture: PASS` という
  一行だけを見ると、負例が「合格してしまった」ように誤読され得る。実際は「証明書自体は
  正直(自己無矛盾)」という別の意味であり、負例としての合否は別行に出る。将来の読者(司令塔・
  Sol・研究者)向けに、per-cert PASS/FAIL の出力ラベルに「self-consistency」等の注記を
  加えるとより安全(機能上のバグではない)。
- 独立の第三系統(本監査用の使い捨て BFS 実装)でも |Q_6|=12(≠|Q_8|=32)を確認済み(§3c)。
  負例が「本当に違う群」であることは数学的にも裏が取れている。

### 5b. BONUS(Ȳ 符号反転)観測の扱い

- コード(`twincell-enum.g` L247-253)・実装ノート双方で「これは壊れていない正しい結果だった
  ため、負例として不採用にした」という判断過程が明記されている。数学的には Γ(2) の別の
  自由生成対を与えるだけで K⁽⁴⁾ の別実現になっている、という説明は妥当に見える
  (符号反転は `Ybar -> -Ybar` であり、`<Xbar,Ybar> = <Xbar,-Ybar>` は一般に同じ部分群を
  生成するので、驚くべき結果ではない)。この扱い自体(BONUS として隔離し、負例カタログには
  含めない)は誠実で、「本来 FAIL すべきなのに見過ごされた」という兆候は見当たらなかった。
  ただし、この BONUS が「頑健性の確認」としてのみ扱われ、**なぜ負例として機能しなかったかの
  数学的説明(部分群の一致)が厳密に証明されているわけではなく、実行結果からの帰納的説明に
  留まっている**点は留意事項として記載しておく(致命的ではない、UNKNOWN 扱いでも良い)。
  → この観点では穴を見つけられなかった。

## 追加チェックリスト(常設観点)まとめ

- **空虚性**: 較正①は実際に marked bijection 機構全体を通した実例(問題なし)。較正②は
  数値較正のみで「kernel 主張」レベルの機構(marked bijection)を一度も通していない
  (§2 で指摘、要修正)。K8 の既知値16は較正として一度も**登録されておらず**、機構を
  通す機会自体が存在しない(§3b、重大)。
- **事前登録**: manifest に窓・生成系・既知値は固定されている(表 L7-12)。silent cap は
  見当たらない(コードの if/case は L や n の値のみに依存し、暗黙の絞りは確認できなかった)。
  ただし §3b の通り、事前登録された既知値(K8=16)が実行コードに接続されていないという
  「登録と実行の間の断線」がある。
- **証明の型**: 負例 fixture は「見つからなかった」ことを非存在の証明として扱っていない
  (FIRE ロックにより標的窓は単に UNKNOWN のまま保持され、`"isolated":"UNKNOWN"` で
  一級の結果として記録される設計)。較正②の個数一致は kernel 主張の証明として不十分である
  ことを implementer 自身も自認しており(実装ノート L84-86)、隠蔽はない。
- **独立性**: `check-twincell.mjs` は `search/twincell-enum.g`・`week3-battery-common.g`・
  `gaplib_common.g` を import していない(ファイル冒頭で明記、実コードでも import 文なしを
  確認)。matrix-mod-L・D_n^3・BFS・marked bijection を全て一から再実装している。
  「照合済み(cross-checked)」という語は実装ノート・manifest 双方で正しく使われており、
  「検証済み(Lean)」との混同は見当たらなかった。

### 問い1: ComputeSettledIsolated の settled/isolated 判定の正しさ

**settled の定義実装は数学的に妥当。ただし node 側の独立再検証には理論的な穴があった
(実測では発現せず)ので【要修正】として記録する。**

- `search/twincell-enum.g` L186-192 のコメントが明記する定義: 「settled: ker(T_{m,f}) = N」
  ⟺「誘導写像 x↦x^u, y↦f⁻¹y^u f が G=Q/N 自身の自己同型であること」。この同値性自体は
  正しい: T_{m,f}: F₂→Q は自由群からの写像なので常に well-defined であり(`docs/
  week1-定義ノート.md` L166 Prop 3.2 の通り、生成元の像を Q の元として直接指定する形の写像)、
  ker(T_{m,f})=N ⟺ この写像が N を経由して Q→Q に降りる(`GroupHomomorphismByImages` が
  `fail` を返さない = well-defined)かつ全単射である、という標準的な群論の事実(単射準同型の
  終域と定域が同位数の有限集合なら全射も従う)に一致する。**この同値性の数学的検証は本監査の
  範囲だが、コード読解の限りでは実装は定義に忠実である**。
- `ComputeSettledIsolated`(twincell-enum.g L193-209): 各 shadow (m,f) について
  `hom := GroupHomomorphismByImages(qrec.G, qrec.G, [qrec.x, qrec.y], [targetX, targetY])`
  → `hom = fail` なら `isSettled := false`(well-definedness の欠如を正しく「非 settled」と
  扱っている)、そうでなければ `IsBijective(hom)` で判定。**位数/濃度の一致だけの弱い判定には
  なっていない**(`IsBijective` は単なる `Size` 比較ではなく実際の写像の単射性まで検査する
  GAP 標準関数)。
- isolated の合成論理(L208): `isolated:=(Length(result.shadows) > 0 and settledCount =
  Length(result.shadows))`。**空 shadow 集合による自明な真(∀ over 空集合)の罠を
  `Length(result.shadows) > 0` の条件で明示的に塞いでいる**ことを確認した。また
  `ComputeSettledIsolated` の内部では各 shadow に対して必ず `true`/`false` のいずれかが
  `isSettled` に代入され(L201-202 の if/else で網羅的)、UNKNOWN のまま素通りする shadow は
  存在しない(1件でも未判定なら `settledCount` が減り `isolated=false` になる設計で、
  「1つでも未判定なのに isolated=true」という抜け穴は見当たらなかった)。node 側
  (`check-twincell.mjs` L355)も同型の安全装置(`detail.length > 0 && settledCount ===
  detail.length`)を実装しており、この観点では一致している。
- **【要修正・本監査での新規発見】node 側の独立再検証(check-twincell.mjs L331-360)は
  「well-definedness」を完全には検査していない**。node のコードは、各要素 g の BFS 正準語
  (spanning tree 上で1つだけ選ばれた代表語)を targetX/targetY で再評価した集合
  `imageSet` の濃度が `elements.length` と一致するかだけを見ている(L345-350)。これは
  「代表語のみを使った関数としての単射性」であり、**BFS 全域木の辺(tree edges)に沿った
  整合性しか保証しない** — 全域木に含まれない辺(非木辺・Cayley グラフの「閉路」)に対応する
  G の関係式が targetX/targetY の下でも成立するかどうかは一度も検査されていない。理論上、
  この弱い判定は「代表語ベースの関数がたまたま全単射になる」ケースを、真の群準同型としての
  well-definedness が欠如していても検出できずに見逃す可能性がある(node 側は GAP の
  `GroupHomomorphismByImages` のように G の全関係式を検査する仕組みを持たない)。
  **本監査でこの懸念を検証するため、GAP・既存 node チェッカーいずれからも独立な第三の
  検証スクリプトを新規に書き**(scratchpad、G の全要素×全4生成元について
  `F(g)*target_gen = F(g*gen)` を悉皆チェックする「完全な Cayley グラフ整合性チェック」を実装)、
  𝒞₁₆・K⁽⁸⁾ 両証明書の settled_detail 全24件(8+16)に対して実行した。結果: **全24件で
  弱いチェック(代表語のみ)と強いチェック(全関係式)が完全に一致し、違反は0件だった**
  (出力: `all 8 entries: ... AGREE`・`all 16 entries: ... AGREE`)。**今回のデータでは
  node 側の弱い判定が偽陽性を生んだ形跡はない**が、これは方法論としての完全性を保証しない
  (今回たまたま discrepancy が出なかっただけ)。
  → **今後の推奨**: node 側の settled 再検証に、全要素×全生成元の Cayley グラフ整合性
  チェック(`F(g)*target_gen == F(g*gen)` を全 g・全 gen について検査、|G|×4 回で計算量は
  軽微)を追加し、「弱い代表語チェック」から「完全な準同型検査」へ格上げすることを推奨する。
  発射を止める理由にはならない(今回は実害なしを実測で確認したため)が、次回以降の standing
  な照合器の頑健性のために記録する。

### 問い2: kernel_certificate の中身 — 数値一致のみか、写像の記録か

**【重大】`kernel_certificate` フィールド自体は実質的に数値(位数/指数)+テキストの
justification のみで構成されており、CLAUDE.mdの「個数一致だけでkernel主張を済ませていない」
原則に照らして単体では不十分。加えて、独立照合器(node)はこのフィールドを一切検査していない。**

- `certificates/twincell/C16.matrix.v1.json` の実際のフィールド(本監査で確認):
  ```
  "kernel_certificate":{"kernel_scope":"PB3","pb3_kernel_index":256,
    "b3_kernel_index":1536,
    "justification":"N = ker(F2 ->> Q_16), Q_16 = <Xbar,Ybar> <= SL(2,Z/16)/{+-I} (2401 (3.32))"}
  ```
  `pb3_kernel_index=256` は同じ証明書内の `universe.pb3_index=256` と**完全に同じ数値の
  重複**であり、`b3_kernel_index=1536` も `universe.b3_points=1536`(=6×pb3_index)の重複。
  `justification` はテキストの説明文であり、N を再構成するための生成元・関係式・元の列挙
  などの**機械可読なデータは何も含まれていない**。K8 側(`K8.dncubed.v1.json`)も同型
  (`pb3_kernel_index=256, b3_kernel_index=1536, justification="N = K^(8) = ker(psi_8), ..."`)。
  この sub-field 単体を見る限り、要求2が警告する「数値一致で済ませている」状態そのもの。
- ただし公平のため付言する: 証明書全体としては、`construction` フィールド
  (`"Q_16 = <Xbar,Ybar> <= SL(2,Z/16)/{+-I}, Xbar=[[1,2],[0,1]], Ybar=[[1,0],[-2,1]]"`)が
  N を定義する具体的な準同型(標準生成元をどの行列へ送るか)を明示しており、この情報と
  証明書内の群構造データ(BFS 閉包で得られる 256 元・関係式)を合わせれば、第三者は N を
  「その準同型の核」として厳密に再構成できる — 完全に無内容な数値だけの証明書ではない。
  **しかし `kernel_certificate` という名の専用フィールドは、この実質的な情報を一切運んでおらず、
  既存フィールドの数値を名前を変えて複製しているだけ**であり、フィールド名が示唆する
  「kernel の明示的な証明書」という機能を果たしていない。
- **さらに重大な点**: `crosscheck/check-twincell.mjs` 全体を検索したが(本監査で実施)、
  `kernel_certificate`・`kernel_scope`・`pb3_kernel_index` のいずれの文字列も
  **一箇所も出現しない** — 独立照合器はこのフィールドを一切読まず、再検算も整合性チェックも
  行っていない。較正③(K8 の |GT|=16)や settled_detail は node 側で独立再検証されている
  のと対照的に、kernel_certificate は node 側にとって**完全に素通りの死んだフィールド**に
  なっている。
- **判定: 【重大】**。要求2が想定した通りの「数値一致で済ませている」状態が実際に存在し、
  かつ独立照合器による裏書きも皆無。発射自体は較正③(数値較正)で通っているため事後的に
  取り消す理由にはならないが、**kernel_certificate という名のフィールドが実際に検証可能な
  形で N を特定する情報(例: N の生成的記述への直接参照、あるいは construction フィールドとの
  一致を node 側が明示的に再確認するロジック)を持つよう改修し、node 側にも
  対応する検査を追加することを強く推奨する**。

### 問い3: 𝒞₁₆=8・K⁽⁸⁾=16 の値自体への影響

**影響なし(コード読解で確認)。**

- `search/twincell-enum.g` の実行順序(L379-422)を確認: `runC16mat := RunWindow(...)` /
  `runK8 := RunWindow(...)` が shadow_total を含む `result` を**先に確定**させ、
  `ComputeSettledIsolated(qrecC16mat, runC16mat.result)` / `ComputeSettledIsolated(qrecK8,
  runK8.result)` は**その確定済み `result` を読み取るだけ**(引数として渡された
  `result.shadows` を走査するのみ)で、`result` 自体やその由来である
  `EnumerateReducedHexagon` の候補列挙・フィルタリングには一切書き戻しがない
  (`ComputeSettledIsolated` の戻り値は新しい rec であり、`run.result` を変更する代入文は
  コード中に存在しない)。settled/isolated 判定は shadow_total 確定後の**純粋な後段追加計算**
  であり、|GT| の値(8・16)を計算する経路とは独立している。
- 較正③(K8 既知値16)は `runK8.result.shadow_total`(settled 計算より前に確定済みの値)
  を直接比較しており、settled 追加の影響を受けようがない構造になっている
  (`calib3ObservedShadowTotal := runK8.result.shadow_total;` は
  `ComputeSettledIsolated` 呼び出しより前の行、L401-402 で行われる)。
- **判定: この観点では穴を見つけられなかった**。「実装漏れがあった状態で出た旧結果」と
  「追加後の新結果」を直接比較する前データは存在しない(標的窓の本走査はこれが初回実行)が、
  コード構造上、settled 追加が |GT| 算出パイプラインに介入する余地がないことをコードの
  読解で確認した(値を書き換える代入文が存在しないことを直接確認済み)。

### 問い4: 「発射直前の追加」は宇宙の事前登録原則に抵触するか

**抵触しない(むしろ manifest 自体がこの観測量を最初から要求していた)。ただし手順上のリスクは残る。**

- `docs/manifest_twincell_v1.md`(本セッション冒頭で読解済み、変更されていない)の
  「観測量(全窓共通・予測は登録しない)」節には当初から
  **「staged counts...・\|GT\|・settled/isolated・kernel 証明書・...」**と明記されている
  — settled/isolated と kernel 証明書は**発射前から事前登録されていた観測量**であり、
  発射直前に新規追加されたのは「宇宙」(位数・生成系・列挙範囲)ではなく、**元から
  約束されていたが実装が漏れていた計算ロジック**である。位数・生成系・列挙範囲(𝒞₁₆=
  行列mod16・K⁽⁸⁾=MakeGn(8)・charming_set の定義等)は一切変更されていないことを
  今回のデルタ検収でも確認した(twincell-enum.g の該当箇所に diff 相当の変更は
  RunWindow/EnumerateReducedHexagon 呼び出し部分になく、settled 関連コードの追加のみ)。
  **よって「宇宙の事前登録」原則(位数・生成系・列挙範囲を先に固定し後から変えない)への
  抵触はない**、という司令塔の見立ては妥当と判断する。
- ただし【軽微】として記録する: 「発射直前にその場で欠落に気づいて実装を追加する」という
  手順自体は、たとえ結果的に無害でも工房の規律としては望ましくない。今回はたまたま
  settled/isolated が計算経路上完全に独立(問い3で確認)だったため実害がなかったが、
  もし settled/isolated 判定がフィルタリングに使われる設計だったら(そうではないが)、
  発射直前の実装追加は「事前登録された宇宙」ではなく「事前登録された観測ロジック」を
  発射直前に事後変更したことになり、より深刻な懸念になっていた。**今後は、manifest の
  「観測量」欄に列挙された全項目が実装済みであることを FIRE ロック解除前のチェックリスト
  (lint 相当)で機械的に確認する運用を推奨する**(今回は implementer の自己点検で
  偶然に発見されたが、次回は見逃される可能性がある)。

### 総合判定(事後デルタ監査)

**残穴あり(以下の2点)。ただし発射自体を無効にする性質のものではないと判断する
(較正③・staged counts・settled/isolated の主判定は健全であることを実測・コード読解の
両方で確認済み)。**

1. 【重大】`kernel_certificate` フィールドが実質的に既存の数値(pb3_index 等)の重複+
   テキストのみで、node 側の独立照合が一切行われていない。証明書全体としては
   `construction` フィールド経由で N は checkable だが、`kernel_certificate` という
   専用フィールド単体はその機能を果たしていない。**発射後の是正事項として明記**
   (次回の証明書スキーマ改訂・node 側検査追加を要求)。
2. 【要修正】node 側の settled 独立再検証が、BFS 全域木の代表語のみに基づく弱い判定で
   あり、全 Cayley グラフ関係式の完全な検査になっていない。本監査で追加実装した独立の
   第三チェックでは全24件で discrepancy は見つからず(実害なしを実測確認)、今回の
   𝒞₁₆=8・K⁽⁸⁾=16・settled 8/8・16/16 の結果を覆す根拠にはならないが、方法論としての
   完全性のために node 側チェックの強化を推奨する。

𝒞₁₆=8・K⁽⁸⁾=16 の数値自体への影響はコード読解で否定した(問い3)。「発射直前の追加」は
宇宙の事前登録原則への抵触ではない(問い4、manifest は当初からこの観測量を要求していた)が、
運用上のリスクとして軽微な指摘を記録した。
