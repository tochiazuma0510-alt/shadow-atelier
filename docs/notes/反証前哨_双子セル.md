## 1. 較正①「二構成全単射一致」— marked factor map 経由か

## 4. staged counts の排他性・hexagon 語規約(A5-CONV)

- `search/week3-battery-common.g` L315-372 `EnumerateReducedHexagon`(GAP 側の正本、twincell
  はこれを import して使い回している、L32/130 で確認)は各 `(f, m)` の組み合わせを

  if-continue 制御フロー**で分類しており、コード構造上、同一候補が複数カテゴリに二重計上され
  ることはあり得ない(L343-366、各 `continue` が次のカテゴリ判定に進むのを阻止)。
  `crosscheck/check-twincell.mjs` L172-190 の独立実装も同型の if-continue 構造。
  両者は「shadow_sum_identity」(candidate_total - h10 - h11 - genFail = shadow_total)を
  それぞれ独立に検算しており(GAP側 L135-137、node側 L247-248)、5証明書全てで
  `shadow_sum_identity:true` を確認した(本監査でも `node crosscheck/check-twincell.mjs` 実行
  で再確認、全 PASS)。
- L315-372 のコメント(week3-battery-common.g L722-728、本監査で確認)によれば
  `EnumerateReducedHexagon` は「quotient shortcut」(`GroupHomomorphismByImages` で実際の
  θ/τ 準同型を群要素に対して直接評価する方式)を使っており、そもそも語規約(prepend/natural)の
  区別が発生しない設計。一方 `check-twincell.mjs` の独立再実装(L133-161)は**語レベル**
  (BFS+prepend 規約)で θ/τ を再現しており、GAP 側とは異なる評価方式でありながら5証明書全てで
  数値が一致した。これは「A5-CONV」規約(`docs/週次定義ノート §1.5.4` 系)がこの独立系でも
  正しく再現されていることの傍証にはなるが、**この監査では A5-CONV 適合テスト
  (`ev(yx^-1) = (1 2 4)`)そのものを twincell 系列(行列 mod L 構成)に対して直接実行した
  形跡は見当たらなかった**(A5-CONV は既存の PSL 系列 `search/manifest_spec_v2_psl.md`
  `PU-F11` で別途通されているものであり、twincell の行列 mod L 構成に対する専用の
  適合テストではない)。
  → **【軽微】**: 数値一致(5/5 全証明書 PASS)は強い状況証拠だが、A5-CONV 適合テストを
  twincell 固有の構成(行列 mod L)に対して明示的に走らせた記録がない。既存 PSL 系列で
  通っている規約を「そのまま使い回して問題ない」という前提は、今回初めて a-系統(行列)の
  θ/τ 評価が絡む場面なので、発射前に一度 A5-CONV 相当の最小テストを twincell 側でも
  明示的に走らせておくとより安全(必須ではないが安価)。

## 5. 負例 fixture・BONUS 観測の扱い

### 5a. 負例 fixture(WRONG_LEVEL6)は実際にバグ検出力を持つか — 実測で確認 PASS(この観点では穴を見つけられなかった)

- 本監査で `node crosscheck/check-twincell.mjs` を実際に実行(改変なし)。結果:
  ```
  window C8_matrix_WRONG_LEVEL6_fixture: PASS
  ...
  [PASS] NEGATIVE FIXTURE (wrong level L=6) correctly rejected: bijection_ok=false, shadow_total=6
  ```
  「window ...: PASS」は**証明書の自己無矛盾性**(claim=recompute)の意味であり、これは
  正しく振る舞う(fixture は正直に作られているので自己矛盾はない)。実際の負例判定は別の行
  `NEGATIVE FIXTURE ... correctly_rejected` であり、`calibBad.ok=false`(bijection 不成立)
  かつ `shadow_total=6≠4` の**両方**が検出されている(L370-373)。総合判定 `all_ok`
  (L383)にも `negFixtureOk` が組み込まれており、これが false になれば `all_pass` は
  出ない設計になっている(fail-closed)。
  → **【軽微】表記上の紛らわしさ**: `window C8_matrix_WRONG_LEVEL6_fixture: PASS` という
  一行だけを見ると、負例が「合格してしまった」ように誤読され得る。実際は「証明書自体は
  正直(自己無矛盾)」という別の意味であり、負例としての合否は別行に出る。将来の読者(司令塔・
  Sol・研究者)向けに、per-cert PASS/FAIL の出力ラベルに「self-consistency」等の注記を
  加えるとより安全(機能上のバグではない)。
- 独立の第三系統(本監査用の使い捨て BFS 実装)でも |Q_6|=12(≠|Q_8|=32)を確認済み(§3c)。
  負例が「本当に違う群」であることは数学的にも裏が取れている。

### 5b. BONUS(Ȳ 符号反転)観測の扱い

- コード(`twincell-enum.g` L247-253)・実装ノート双方で「これは壊れていない正しい結果だった
  ため、負例として不採用にした」という判断過程が明記されている。数学的には Γ(2) の別の
  自由生成対を与えるだけで K⁽⁴⁾ の別実現になっている、という説明は妥当に見える
  (符号反転は `Ybar -> -Ybar` であり、`<Xbar,Ybar> = <Xbar,-Ybar>` は一般に同じ部分群を
  生成するので、驚くべき結果ではない)。この扱い自体(BONUS として隔離し、負例カタログには
  含めない)は誠実で、「本来 FAIL すべきなのに見過ごされた」という兆候は見当たらなかった。
  ただし、この BONUS が「頑健性の確認」としてのみ扱われ、**なぜ負例として機能しなかったかの
  数学的説明(部分群の一致)が厳密に証明されているわけではなく、実行結果からの帰納的説明に
  留まっている**点は留意事項として記載しておく(致命的ではない、UNKNOWN 扱いでも良い)。
  → この観点では穴を見つけられなかった。

## 追加チェックリスト(常設観点)まとめ

- **空虚性**: 較正①は実際に marked bijection 機構全体を通した実例(問題なし)。較正②は
  数値較正のみで「kernel 主張」レベルの機構(marked bijection)を一度も通していない
  (§2 で指摘、要修正)。K8 の既知値16は較正として一度も**登録されておらず**、機構を
  通す機会自体が存在しない(§3b、重大)。
- **事前登録**: manifest に窓・生成系・既知値は固定されている(表 L7-12)。silent cap は
  見当たらない(コードの if/case は L や n の値のみに依存し、暗黙の絞りは確認できなかった)。
  ただし §3b の通り、事前登録された既知値(K8=16)が実行コードに接続されていないという
  「登録と実行の間の断線」がある。
- **証明の型**: 負例 fixture は「見つからなかった」ことを非存在の証明として扱っていない
  (FIRE ロックにより標的窓は単に UNKNOWN のまま保持され、`"isolated":"UNKNOWN"` で
  一級の結果として記録される設計)。較正②の個数一致は kernel 主張の証明として不十分である
  ことを implementer 自身も自認しており(実装ノート L84-86)、隠蔽はない。
- **独立性**: `check-twincell.mjs` は `search/twincell-enum.g`・`week3-battery-common.g`・
  `gaplib_common.g` を import していない(ファイル冒頭で明記、実コードでも import 文なしを
  確認)。matrix-mod-L・D_n^3・BFS・marked bijection を全て一から再実装している。
  「照合済み(cross-checked)」という語は実装ノート・manifest 双方で正しく使われており、
  「検証済み(Lean)」との混同は見当たらなかった。
