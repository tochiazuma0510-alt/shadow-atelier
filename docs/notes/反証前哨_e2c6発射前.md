## 問1: ob 射影は両系統(GAP/node)とも批准定義に忠実か。偶然一致の余地は

**忠実。** 両実装とも `ObFromQPair`/`obFromQPair` で
`ob = [q_theta - 3^{-1}(1+theta)q_N] mod R`、`ob_a=v[u4]`, `ob_b=v[u2]` を実装しており、
式・添字ともコード上一致を確認した(GAP L395-403、node L222-228)。θ の作用行列
(`ThetaOnCMat`)は GAP が `agree6_claude.json`、node が `agree6_sol2.json` という
**別ファイル**(sha256 相異を確認)から独立に構築しており、θ(u4)=-u4・θ(u2)=+u2・
θ(t5)↔θ(t6)・θ(u1)↔θ(u3) という規約が両ファイルで一致していることは実行時の
self-check(`theta^2=id`、`d_theta_formula` 整合)で担保されている。

**ただし正直な限定**: 「二系統」の独立性は主に**データ系統(A/B)の分離**にある。
ob 商式そのもの(`ObFromQPair` の中身)は GAP・node とも**同一の仕様文書 3 本**
(manifest v2・委嘱16・便22)を読んで実装者(同一実装者)が書き下ろしたコードであり、
「実装者が式を誤読した場合、両言語で同じ誤りが複製される」リスクは論理的に残る
(この点は `実装_e2c6掃引.md` 自身も入力規律として明記しており、隠していない)。
これを緩和しているのは、F1/F2 fixture の**期待値**(ob=(0,0)/(1,0)/(0,1))が
実装コードからではなく **数学者(委嘱16 §4・§3 ラベル整合)の手計算由来**である点 ——
実装が式を誤読していれば、この外部由来の期待値との照合で捕捉される设计になっている。
完全な独立ではないが「空虚な同意」でもない。

## 問3(新規発見): q_N ≠ 0 で商の「訂正項」計算が一度も演習されていない 【要修正】

## 問4: F4(M 系)は空虚でないか。自己修正 2 件は正しい修理か

**空虚でない。修理は妥当。** 前任の指摘した「基準未定義」は 委嘱16 §5(M1-M8)・
便22(F10)で埋まり、manifest v2 が明記。実装ノートが記録する自己発見バグ2件を検証:

- **M2/M3 の前提誤り(修正1)**: 「E23a/E23b は任意の f に成り立つ恒等式ではなく、
  f が線型段の解であることが前提」という診断は正しい(命題の証明が θ̄f̄=-f̄・
  𝒩̄f̄=-Ē_m を明示的に使っている)。修正後の M3(任意の m 非依存の安全な合成系の
  真正な核解で検査)・M2(m=0 限定)は前提を満たす入力に絞っており、
  「前提を満たさない入力での失敗」を「反例」と誤読していた古い実装よりも健全。
- **mod R 還元忘れ(修正2)**: 「2d=0 は R 上の恒等式であり整数上ではない」という

**M2 の m=0 限定の設計は盲検を守れているか**: 限定的だが正当。ただし、

実際には **Ē_m(0)=0 が恒等的に成り立つため、m=0 における真の対象系(banned な

実害はない(m=0 の可解性は Ē_m(0)=0 という構造的事実から自明に従い、開示禁止の

「m=0 は override ではなく、構造的に real と一致する」と manifest/実装ノートに
明記した方がよい。【軽微】
