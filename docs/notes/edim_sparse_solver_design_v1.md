# EDIM 疎行列版ソルバー設計スペック v1(実装係起草・k=11/12 前提工事)

- 起草: 影工房 実装係・2026-08-06
- 委嘱: 司令塔(裁定658 follow-up、GHA 16GB runner 前提への見積り更新込み)
- 対象: `search/edim_semidirect_v1.py` の `GradedLie.coords_of_ambient`(密行列
  ambient×basis ソルバー)を疎行列版へ置き換える。k=11(dense 22.8GB)・
  k=12(dense 188GB)は現行密実装では 16GB runner でも不能 — この工事なし

## 0. 現状の問題(再掲・数値更新)

`_get_solver(degree)` は次数 `degree` の**アンビエント全語空間**(𝔫 側は
3^degree 語)× **基底次元**(Witt(3,degree))の**密** numpy int64 行列を
構築してから Gauss 消去でピボット行を選ぶ。

| k | dim_n | ambient(3^k) | 密行列 GB | 疎(見積り)MB |
|---|---|---|---|---|
| 9(実測済) | 2,184 | 19,683 | 0.34 | ~11 |
| 10(実測済) | 5,880 | 59,049 | 2.78 | ~60 |
| **11** | 16,104 | 177,147 | **22.8**(★16GB超過) | ~330 |
| **12** | 44,220 | 531,441 | **188**(★論外) | ~1,800 |

疎の見積りは各基底列(Lyndon 括弧展開)の非零項数を最悪 `2^(degree-1)`
(括弧を取るたびに高々倍化)として `dim_n × 2^(degree-1)` を非零総数と
し、1 非零あたり (row:int64 8B + value:int64 8B + 若干のオーバーヘッド
4B) ≈20B で概算。**実測ではこれより疎になるはず**(低次数の部分木は
展開後に語が重複・相殺し 2^(k-1) に届かないケースが多い — k=9,10 の
密行列実測とはまだ突合していない、要検証)。

## 1. 表現(疎化そのものは既にほぼ完了している)

`self.ambient[k]` は元々 **dict(word_tuple → coeff)** のリスト(基底ベクトル
ごとに疎表現)で保持済み — 疎行列化で新規に必要なのは
**「アンビエント→基底座標」変換ソルバーだけ**であり、基底の保持形式は
変更不要。

## 2. ピボット選択(密 Gauss 消去 → 疎対応版)

### 2.1 なぜ単純な「貪欲行選択」だけでは不十分か

列 c ごとに「まだ使われていない非零行を 1 つ取る」だけの貪欲法は、
**選んだ basis_dim 行の部分行列が可逆である保証がない**(値の依存関係
まで見ないと、非零パターンだけでは線形独立性を保証できない)。

### 2.2 採用する方式: 疎 Gauss 消去(部分縮約・fill-in 追跡)

- 行を **dict(row → dict(col → value))**、列を **dict(col → dict(row →
  value))** の双方向インデックスで保持(標準的な疎行列消去の作法)。
- 列 c=1..basis_dim の順に:
  1. その列で「未使用行のうち非零成分数が最小の行」を選ぶ(Markowitz 基準
     の簡易版 — fill-in を抑える)。
  2. その行をピボットとして正規化(逆元を掛ける)。
  3. **他の列**からこの行の寄与を消す(疎な列インデックスを辿るだけで
     済む — 密のように全列を舐めない)。
  4. fill-in(消去で新規に非零になったエントリ)を row/col 両インデックス
     に追加。
- **fill-in 監視**: 各消去ステップ後、疎密度(非零数/basis_dim²)を記録し、
  閾値(例: 30%)を超えたら **`SPARSE_FILLIN_EXCEEDED / STOP`**(密実装へ
  自動フォールバックしない — 想定外の稠密化は数学的に「基底の選び方が
  悪い」可能性を示唆するので実装バグ第一疑いで報告)。

### 2.3 検証ステップ(密版と同じ規律を維持)

密版と同じく、求めた座標を基底へ再合成して元のベクトルと一致するかを
**必ず**確認する(疎版でも省略しない — fail-closed の生命線)。

## 3. 大素数(2147483647 等)でのオーバーフロー安全性

疎消去でも「単項の積は安全・複数項の和は危険」という制約(本セッション
で発見した int64 溢れバグと同じ)は変わらない。消去の各ステップは
**単一の行×スカラー**操作(単項積)なので密版の `_get_solver`/
`_mat_inv_modp_numpy` と同じ安全域に収まる — 新規のオーバーフロー
リスクはこの点では増えない。

## 4. k=11/12 の見積り(GHA 16GB runner 前提)

- **k=11**: 疎行列本体は ~330MB(非零推定)。fill-in を仮に 5〜10 倍まで
  許容しても 1.5〜3GB — 16GB runner に十分収まる**見込み**(実測未検証)。
- **k=12**(691 番地 — 別枠だが見積りに含めるよう指示あり): 疎本体
  ~1.8GB。fill-in 5〜10 倍で 9〜18GB — **16GB runner でもギリギリ〜超過
  の可能性**。ここは実装後に k=11 の実測 fill-in 率を見てから改めて
  判定すべき(k=12 は別枠・本工事の対象外だが、疎化なしには k=11 同様
  不能な点は確定)。

## 5. 実装範囲・段取り(委嘱への回答)

1. `SparseGradedLieSolver` クラスを新設(`_get_solver` を置き換え、
   `GradedLie` から差し替え可能にする — 既存 k≤10 の呼び出し側コードは
   無変更で動くようインターフェースを揃える)。
2. k=9,10 の**既存密実装の結果**(GHA 実行待ち)と**疎実装の結果**を
   同一 degree で突合し、一致することを確認してから k=11 へ進む
   (疎化自体の正しさを検証する回帰ゲート — 密版が「正」の基準)。
3. k=11 を疎版で実行、fill-in 率・実メモリ・時間を実測・報告。
4. k=12 は**別途認可を待つ**(691 番地は別枠と明記済み)。
