## 問1: 一次出力=重複度表の実装は本物か

**部分的に本物、しかし G1 の「独立性」には限界がある。**

- `BuildJ3MultTableShortcut`(λ-shortcut、便24 eq 8.3 の affine 公式)と
  `BuildJ3MultTableBruteForce`(全 `Prod(K_orders)` 点を悉皆列挙し、非線型の `QFirstCond`
  を厳密評価)は実際に**別コード**であり、1 witness で終わらせていない ——
  m=0,1,2,3 で `|L|` は 512/4096/512/1024 と有意に複数の witness を実際に走査している
  (m=1 で 4 生成元 rank 4、m=0/2/3 は生成元数が少なく span も小さいが、いずれも rhs=0 の
  中心項テストであり c=1 系列専用ではない — 前回 j=2 監査で見つかった「中心項が一度も
  試されない」型の空虚性は再発していない)。
- ただし G1 の brute-force は **同じ SNF/TestAtJ が返した K_generators/f0 を土台に
  同じ Abar モデル内で**動いており、線型段の解自体(K_m^(3) の生成元が本当に
  `ker(1+θ̄)∩ker(N̄_m)` を尽くしているか)を検証する第三の経路ではない。これは
  「λ-shortcut という近似の正しさ」は検出できるが、「線型段モデルそのものの正しさ」は
  検出しない、という射程の限定であり、意図的な設計(G1 は偽陽性検出器であって
  線型段検証器ではない)として理解すべき。G3(route-G)がこの限定を別の角度から
  部分的に埋めている(q_θ/q_N の closed-form を genuine PcpGroup 積と突合)が、
  G3 も「first-condition」自体を検査対象にはしていない。

## 問2: ob 読み出しの商意味論(R[2]a⊕(R/2R)b̄・R=4)は忠実か 【重大寄りの要修正】

**G4 は必要条件を検査しているが、実際の R=4 における `ObFromQPair` 呼び出しが
本ファイル中一度も演習されていない。**

`grep` で確認した通り、`search/e2c6j3-sweep.g` 内で `ObFromQPair` が呼ばれているのは
G2b の **R=2** ケースのみ(j=2 ゲートとのドリフト検査)。G4 は
`(1+θ)ker(N_C)` を R=4 で再計算し、u4 成分が `{0,2}` に収まること・u2 が mod 2 で 0 に
なることを検査しており、これは 委嘱16 (0.3)(0.6) の**必要な構造的前提**を裏付ける
正しいテストだが、**`ObFromQPair(qTheta, qN, 4)` という実際にコード上使われる関数を
R=4 の入力で一度も呼んでいない**。つまり:

- j=2 側への「密輸」(j=2 の成分読みをそのまま j=3 に持ち込む誤り)は G2b が正しく
  ガードしている(R=2 限定で明示チェック)。
- しかし対称的に、**「R=4 での ob_a/ob_b が実際に `{0,2}`・mod2 意味論通りに出るか」を
  確認するコードパスがどこにも存在しない**。もし `ModInverse(3,4)` の計算や
  `ThetaOnCVec` の R=4 での挙動に off-by-one 的なバグがあっても、G4(kernel のみを見る)
  にも G2b(R=2 のみ)にも捕捉されない。これは前回 j=2 監査の問3
  (「訂正項コードが nonzero q_N で一度も演習されていない」)と**同型の空虚性**であり、
  未対応のまま持ち越されている。

**要求**: 発射前に、安全な合成 q_θ/q_N ペア(実データを開示しない値)を
`ObFromQPair(qTheta, qN, 4)` に渡し、`ob_a ∈ {0,2}` であることを確認する fixture を
G4 系列に追加すること。コストはほぼ無料。

## 問3: 便24 §F8 の転写は逐語か。前提破れ時のガードは 【要修正・複数】

boxed 式 (8.1)-(8.4) 自体の転写(コードコメント L46-56)は §F8 本文と照合して**逐語一致**
を確認した。しかし §F8「j=3 実装へ要求する計算」の 6 項目のうち、**実装されているのは
実質 3・4 のみ**(重複度表とその総和=|K|)である。1・2・5・6 は未実装:

1. **「不可解なら dual witness を出す」が未実装**: `TestAtJ` の不可解分岐は
   `rec(solvable:=false, failRow, modulus)` のみを返し、`RunRealSweepC6J3` の負例証明書
   (`linear_stage_empty_c6j3`)も `failRow`/dual witness を一切記録しない。実 m>0 で
   不可解な系が出た場合、§F8 が要求する診断情報が証明書に載らない。
2. **「各 generator に (8.3) を適用した 2×d bit matrix とその rank を証明書へ入れる」が
   未実装**: 現行証明書には `ob_table`(最終結果)のみで、λ 適用後の bit matrix も
   明示的な rank フィールドもない(span サイズは `total/mult` から逆算は可能だが、
   明示的に保存されておらず、便24 の要求を字義通り満たしていない)。
3. **項目5「ob-zero branch ごとに中心補正数 |kerΛ|=2^{e+1}=8 を掛けた full mass と
   直接群積 M8 を照合する」が丸ごと未実装**: リポジトリ全体を grep しても `M8`・
   `kerLambda` 相当の実装は見当たらない。これは 6 項目の中で**最も独立性の高い検査**
   (affine-linear モデルの外側、直接群積という第三の経路)であり、これが欠けていることは
   G1/G3 だけでは埋まらない。G3(route-G)は q_θ/q_N の closed-form 検証であって、
   first-condition の mass 検証ではない。
4. **項目6「mod 8 での m→m+32 周期性、0≤m<32 が基本周期」の周期性 fixture が
   未実装**: `m+32` や周期性に関する言及はコード中に一切ない。事前登録窓
   `m∈{0,...,63}` の後半(32-63)が前半の独立確認になっているかどうかを本走査前に
   確認する機会を逃している。

**前提破れ時のガードについて(問3後半の直接要求)**: `k_w≡0(mod 8)` の前提は
manifest・実装ノートとも「安全な合成系のみで検証・実 m>0 は未検証」と正直に申告している。
しかし fixture 側のコードを見る限り、`kwZeroOk` フラグは **fixture pass 内でのみ**
評価され、`RunRealSweepC6J3`(実 64 系本走査)の中では **k_w=0 の再チェックが
一度も行われていない**。もし実走査で `k_w≠0` の生成元が出現した場合(前提が破れた場合)、
現行コードは (8.3) の λ 公式をそのまま適用し続け、**警告もエラーも出さずに誤った
multiplicity table を証明書に書き込む**。これは司令塔発注が名指しで要求した
「黙って進まず検出・停止するガード」が**存在しない**ことを意味する。【重大】

**要求**: `RunRealSweepC6J3` 内、各 m で `resD.kgens` を得た直後に
`k_w mod 8 = 0` を全生成元について再検証し、破れていれば
(a) その m の証明書を `"claim":"precondition_violated_c6j3","k_w_nonzero":true` 等の
専用スキーマで書き出し、(b) λ-shortcut によるテーブル生成をスキップする
(brute-force のみに切り替えるか、UNKNOWN として明示する)処理を追加すること。
これは発射条件②のブロッカーとして扱うべき(司令塔発注が名指しで要求した項目)。

## 問4: e2c6-common-data.g の逐語コピー(DRY 違反)とドリフト検出

コピー自体は妥当な設計判断(確定済み j=2 ファイルを不変に保つ)。本監査で
`BASIS21`・`ThetaTable21`・`SigmaTablePoly21`・`EmComponents21`・`KappaTerms`・
`DThetaFormula`・`DSigmaFormula` の全ブロックを `search/e2c6-sweep.g` と文字列比較し、
**現時点で byte-identical であることを確認した**(コピーの正確性そのものに疑義なし)。

ただし **G2b はドリフト検出として不完全**: G2b が検査しているのは
`ObFromQPair`(商公式)の入出力一致のみであり、上記の生テーブル7個(全体で数千文字)の

`ObFromQPair` 自体は無傷なので G2b は PASS し続ける(自己整合性チェック
`E2C6_thetaSqOk` 等は「コピー内で自己矛盾がないか」であり「原本と一致するか」ではない)。
【要修正・軽微】: 生テーブルの原本一致を保証する自動チェック(例: 両ファイルの

追加することを推奨。現状は falsifier が手作業で確認して初めて担保される状態であり、
恒久的な証拠として証明書に残っていない。

## 問5: 封印遵守の確認

**漏洩なし。** リポジトリ全体を `F7`・`branch-wise`・`prediction` 等で grep し、
全ての言及を確認した結果、すべて「§F7 は読んでいない/封印されている」という
**メタ言及**のみであり、§F7 の内容(実際の予測値・分岐パターン)を示唆する記述は
見当たらなかった。特に G1 の設計(manifest 自身が明記)は「特定の到達パターンを
主張しない」という形で、fixture の振る舞いから逆算的に §F7 の予測を漏らすリスクを
意図的に避けている ——これは正しい設計である。

**紛らわしい点(実害なし)**: コード・manifest 中の「F7」という語は**二つの異なる対象**
を指している ——① `sol_reply_24_d2.md` §F7(封印された予測、未読)と
② `search/e2c6-sweep.g` 自身のフィクスチャ名 F7(route-G 群積突合、j=2 で既に
公開・実行済み)。今回の G3(「F7 群積突合の j=3 セル追加」)は②を指しており、
①とは無関係。コード中のコメントは都度明示的に区別しており(「e2c6-sweep.g's F7」等)
実務上の混乱は起きていないが、この命名衝突自体は将来の読み手が誤読する余地があるため
記録しておく。【軽微】
