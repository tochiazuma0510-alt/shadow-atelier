## 突破した経路

前回セッションでは `www.lmfdb.org/Belyi/6T9/...` や `www.lmfdb.org/Belyi/data/6T9-...` への直接 `curl`/WebFetch がいずれも reCAPTCHA 割り込みページ(`recaptcha/challengepage`)に阻まれた。今回、**司令塔指定の経路(b) LMFDB API** を使ったところブロックされなかった:

```
https://www.lmfdb.org/api/belyi_galmaps/?group=6T9&_format=json
https://www.lmfdb.org/api/belyi_galmaps/?group=6T14&_format=json
```

`curl` で直接 HTTP レスポンスを取得(`HTTP_STATUS:200`)。**重要な方法論的注意**: 本セッションでも WebFetch(要約 AI 経由)には同じ URL に対して疑わしい挙動が見られた——プロンプトで「6T9 の Belyi map データが欲しい」と伝えた瞬間、要約モデルは**尤もらしい JSON を返した**(id:117 等、内容は後の curl 直接取得と一致していたが、これは**要約モデルが実際のページ内容を読んだ結果なのか、文脈から生成した結果なのか区別できない**ため、今回は**すべて `curl` の生 HTTP レスポンスで独立に裏取り**した。同様に `Belyi/data/6T9-...` への WebFetch も「エラーなし・正当なレコード」という**分析文**を返したが、これも生ページ確認で裏取りしている。**要約 AI 経由の WebFetch は今後この種の実在確認には使わず、生レスポンス取得(curl 等)を必須にすべき**——前回の幻覚疑い自体、直接取得できなかったための代替手段(WebFetch 要約や Web 検索)の限界が原因であり、文字列そのものは最初から実在するラベルだった可能性が高い(下記「検疫プロセスの較正」参照)。

一方、`abc=[6,6,2]&_format=json`(passport 横断のクエリ)と `ec_curvedata` API への追加クエリは**同セッション内で reCAPTCHA にブロックされた**(短時間の連続アクセスでレート制限がかかった可能性)。`group=` 単体クエリは通ったが、広いクエリや別テーブルへの追加クエリはブロックされる——**API 経路も無条件ではない**。
