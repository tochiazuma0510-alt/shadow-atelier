# Luna reply 384 - A4 canonical exact batch v2

## 結果

指定された 3 executable を新規作成した。v13/v15 の arithmetic、early
completed-row checkpoint、resume、terminal、receipt/checkpoint schema は維持し、既存の
dual-column loop だけを canonical current-basis batch に変更した。production、GHA、
SELFTEST、git、network は実行していない。

固定 dual の complete accumulator ごとに、両側とも同じ ascending
`(context, relation, token)` 順を走査する。各 literal raw boundary column は、直前までの
batch 挿入を含む **current combined basis** で再 reduction され、remainder が非零の
場合だけ既存 `add_boundary` に渡される。最大 64 rank-rise、または roster 枯渇で止まり、
外側の既存 target reduction へ戻る。boundary-only pretest、scale、sum、raw identity の
変更はない。

## Public ABI と fail-closed gates

- public correlation object は従来どおり
  `pair_count / accumulator_digest / selected / complete` の 4 field だけである。
- canonical nonzero roster は `correlate_private` の一時的な private return だけに置き、
  `live_duals`、public correlation digest、receipt、checkpoint に格納しない。
- `selected` は従来どおり最初の canonical nonzero candidate である。
- `CANONICAL_BATCH_CAP == 64` を producer/checker の各 correlation で fail-closed に確認する。
- nonzero roster branch では accepted count を `1..64` と要求し、zero branch では roster
  が空であることを要求する。
- 各 accepted candidate は直前に `combined.reduce(column)` が非零だったものだけであり、
  `add_boundary` 後の combined rank がちょうど 1 上がることを要求する。
- complete correlation ごとの dual-chain 増分はちょうど 1、accepted item ごとの
  query-event-chain 増分はちょうど 1 で、その event schema はすべて通常の
  `BOUNDARY_RANK_RISE` であることを要求する。
- 各 insertion record は同じ fixed dual digest、complete accumulator digest、pair count を
  保持しつつ、実際の selected column、ledger、chronological rank を記録する。
- `accepted_batch_size` は直近 correlation の実 accepted rank-rise 数 `1..64`、真の
  zero correlation では 0 である。
- v16 は v14 を import せず、独立 v15 owner から accumulator、canonical roster、raw
  translation、current-basis reduction、insertion を再計算する。

## Full-correlation 削減見積り

従来は nonzero correlation 1 回につき rank-rise は必ず 1 だった。今回は 1 回につき実際の
independent rank-rise 数を `a` (`1 <= a <= 64`) とすると、その区間の full-correlation
per rise は `1/a` になる。full 64 batch なら最大 64:1、すなわち同じ 64 insertion を
singleton loop で行う場合に比べて 63 回の直後再 correlation を省く。依存 candidate の
skip、roster 枯渇、target の早期 MEMBER 化により実 `a` は小さくなり得るため、wall-time
短縮量は production 未実行の現時点では宣言しない。zero-correlation/K terminal の 1 回は
削減対象ではない。
