## F5【要修正】mod \(2N_{\rm ord}\) 精密化は正しいが、名称・一般性・「必須」の三点を分けよ

写像
\[

\]
は奇数類への全単射で、単元条件の下では
\[

\]
となる。この精密化自体は正しい。以後は、定義ノートの有限版 \(\chi_{\rm vir}\bmod N_{\rm ord}\) と区別して
\[
\widetilde\chi_N([m,f]):=2m+1\bmod 2N_{\rm ord}
\]
などと呼ぶのが安全である。

修正点は次の三つ。

1. 一般の \(N\) では \(\mathrm{GT}(N)\) は群ではない。従って補題 B4 の「\(\chi_{\rm vir}:\mathrm{GT}(N)\to(\mathbf Z/2N_{\rm ord})^\times\) は群準同型」は、**composable な shadow に対し乗法的**、または **\(N\) が isolated のとき群準同型**と直す必要がある。定理 B では (ii) の後に使うので結論は壊れない。

3. 「\(C_4\) が見えるのは mod 60 だけ」は強すぎる。mod 30 へ落としても
   \[
   \{1,13,37,49\}\mapsto\{1,13,7,19\},

   かつ \(13^2=19,\ 13^3=7,\ 13^4=1\pmod{30}\) なので、核の \(C_4\) 構造は既に見える。mod 60 の利点は \(m\bmod30\) を一意に復元し、四元を元の整数表示のまま保つことである。

★ \(m\) は mod \(N\) だが \(2m+1\) の自然な忠実法は mod \(2N\) である。ただし「より細かい」と「従来の射影が誤り」は同義ではない。

## F11【要修正・条件付き合格】封印予測プロトコル

ハッシュ先行記帳は「後から予測を書き換えなかった」ことの証拠として有用で、J を較正として撃つ判断も妥当である。ただし現在の方式には二つの限界がある。

- append-only という運用宣言だけでは時刻を第三者に固定しない。計算前の git commit など、変更不能な時点の錨が必要である。

標準化するなら、対象定義の hash、予測 field 一式、証明文書版、128-bit 以上のランダム nonce を canonical JSON にし、その**正確な byte 列**の SHA-256 を計算前 commit に記帳する。nonce と平文は実装レーンから読めない場所に保持し、開封時に byte 列と nonce を公開して再計算する。この形なら commitment と blinding を区別できる。
